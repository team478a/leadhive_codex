# Phase C4: 停止理由別のLead Completion作業キュー

## 目的

C3の固定リスト診断から、確認が必要な企業・店舗を見つけ、既存の企業詳細へ直接進める。下書き・承認・送信・再解析を自動実行するジョブキューではなく、Humanの確認作業を支援する一覧である。

## 操作

1. ダッシュボードの「リスト完成率」でProjectと固定対象を選択。
2. 「窓口診断を集計」を実行。
3. 「停止理由別の作業キュー」で状態と停止理由を選ぶ。
4. 会社名、DM未準備の理由、窓口別の理由・次の作業を確認し、「詳細を開く」で既存の企業詳細を開く。
5. 必要な確認・修正を既存画面で行った後、固定リストを再集計する。

状態は窓口READY／REVIEW／HOLD／BLOCKED、DM未準備／DM READY、結果不明・証跡のHuman確認を選択できる。状態と理由はAND条件。理由の件数は受信済みLeadごとに一度数え、一つのLeadに複数理由がある場合は複数分類に現れる。理由の選択肢の件数は受信済み全体であり、状態フィルタ適用後の件数とは区別する。表示は25件単位で、フィルタ変更時は先頭ページへ戻る。

## 安全境界

- 部分集計では受信・検証済みページだけを一覧へ追加。未診断分を推定しない。再集計時は旧一覧を消去し、中断後の遅延応答を混ぜない。
- Company名は診断APIの既存Project境界内で追加取得する。削除・統合された固定対象は名前nullとし、詳細ボタンを無効化。固定分母は維持。
- 詳細遷移は追客完了・延期と別のcallbackを使用。既存GET `/api/companies/{id}`を再取得し、現在のProjectとの一致も確認。権限失効・削除時は既存APIの拒否を表示し、代替企業を勝手に開かない。
- DM READYは現在の有効準備であり、APPROVEDや送信許可を意味しない。窓口READYとも区別する。
- BLOCKEDは理由確認用で、下書きやスコアで解除しない。UNKNOWN／証跡不一致はHuman確認を表示し、自動再送しない。
- 送信実行履歴を表示するが、C3と同様に検証可能なC2連携履歴だけを対象とする。旧経路の結果・共有窓口・重複は企業詳細と既存履歴画面で再確認する。
- 一覧はページ取得時点の観察結果で、現在の承認・送信判定を代替しない。集計は状態や台帳を書き換えない。

## 変更範囲

`cohort_destinations.page`に`company_name`を追加。Model、Migration、新規endpoint、認証、送信APIの変更なし。Frontendの`CompletionWorkQueue`と表示用型を独立ファイルに分離し、診断画面に受信済み行を保持する。App→Dashboard→固定診断→企業詳細の専用導線を追加。企業詳細は既存読み取り・編集UIを再利用する。

## 検証

専用_test DBの合成データでページ診断・Project／viewer境界・削除対象を検証。desktop/mobileで部分集計と中断、26件のページ切替、理由／状態の組み合わせ、フィルタ後のページリセット、該当なし、選択企業の詳細を確認する。UNKNOWNと削除候補のUI条件はテスト内の応答fixtureで確認し、送信履歴を実DBへ捏造しない。画面テストは外部URL・送信・dispatch・承認endpointへのアクセスがないことも確認する。

実100店舗の再解析・実送信・稼働環境反映は今回行わない。既存の500kB超bundle警告は別課題。

今回のローカル結果: 関連Backend 44件、desktop/mobile E2E 2件、Frontend typecheck/lint/build、Backend全体Ruff lint、変更2ファイルのformat検査、変更サービスのmypyに成功。専用DBのMigration upgrade/model差分とE2E API起動も確認。全体のローカルformat検査は既存4ファイルのcheckout改行混在だけを指摘し、HEADと改行を正規化した内容が同一であることを確認した。GitHubのLinux CIで全体を再検証する。

## 次工程候補

確認作業後に同じ固定リストと絞り込みへ戻り、更新対象を再診断する導線を追加する。観察結果を送信許可へ転用せず、Human承認・安全guardを維持する。
