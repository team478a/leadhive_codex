# CSV取込ワークフロー 実装記録

## 大量候補の営業準備（送信なし）

企業収集画面の「営業準備をまとめて実行」から、登録済み候補を最大300件ずつ処理する。公式サイトの補完、Web解析、目的に合わせたAI判定、連絡可否確認、会社別Draftを一つのバックグラウンドジョブで実行する。承認、EmailDelivery、FormDeliveryを作成せず、送信には接続しない。

1. Projectの営業目的とTargetProfileを確認する。
2. 最大件数、最低スコア、検索・AI回数上限、連絡方法を指定する。
3. 「営業準備を開始」を押し、企業ごとの文面準備済み／要確認／準備停止／エラーを確認する。
4. 公式サイト候補の一致が曖昧なものはURLを確認し、企業情報を修正する。文面は企業一覧の既存営業文面画面で確認する。
5. 中断したジョブは「未処理から再開」。要確認・エラーとして処理済みの企業は原因を確認して新しい準備を作成する。

対象は既定で登録順の先頭300件。「先頭から除く件数」を300、600…と指定して後続を処理できる。APIのcompany_idsで特定候補を指定でき、最新ジョブの「要確認・エラーだけ再準備」でも該当企業だけ指定する。これは新しいジョブと新しい回数上限を作る操作であり、回数を引き継ぐ「未処理から再開」と区別する。300件をすべてAI判定・文面作成する場合は最大600回必要で、既定AI上限60回では残りが要確認となる。検索既定上限30回。予算は再開後も累積し、外部呼び出し前に記録する。金額上限やトークン上限ではなく呼び出し回数上限である。

公式サイトは店舗名と番地を含む住所、または電話番号が一致した場合だけ自動採用する。ポータルURL、robots禁止、危険URLを迂回しない。曖昧な候補は最大5件を保存し、そのうち最大2件のみWeb照合する。住所の表記揺れ等で一致できない場合も要確認となる。

過去のAI判定には営業目的の履歴がないため、このジョブで一度再判定する。営業目的・地域・TargetProfileが途中変更された場合は要確認。中断したAI／文面呼び出しは重複課金防止のため自動再実行しない。フォーム解析はルールのみを使用し、曖昧な判定を追加AI課金で補わない。準備済みは「送信可」や「承認済み」を意味しない。実送信時の最新安全判定は既存経路に残る。

API: POST/GET /api/projects/{project_id}/sales-preparation、POST /api/sales-preparation/{job_id}/resume。Humanログイン必須、開始・再開はowner/editor、参照はviewer可。Agent credentialは既存Human境界で拒否。停止は既存OperationJob cancelを利用する。SalesPreparationItemとOperationJobを保存し、完了項目は復旧時に再処理しない。

Migration e3b7d92f410aはc7a24d9e601bの後に追加。履歴が存在する状態でのdowngradeは拒否する。既存送信ジョブ・承認基盤は変更しない。必要な設定、公式サイト、連絡先が不足していれば完全自動で300件の文面ができる保証はない。

検証（2026-10-05）：Backend全260テスト通過後、最終差分の営業準備・OperationJob 23テストを再実行して通過（計265個の現行テストをカバー）。実PostgreSQL・模擬外部APIで300社・600回の判定／文面生成を確認し、EmailDelivery・FormDelivery・ApprovalRequestは0件。予算保持、途中再開、完了済み復旧、AI結果不明時の保留、営業目的変更、Suppression、viewer／Agent拒否、フォームAIフォールバック停止、開始位置と個別対象、downgrade履歴保護を確認。

Frontend typecheck／lint／build通過。既存PC／モバイル6 E2Eが通過し、最終変更後の店舗取込・営業準備4 E2Eも通過。空の専用DBでupgrade→downgrade→upgradeとAlembic check通過。ローカル確認用18984へバックアップ後に反映し、API／worker稼働、health/database OK、会社100件・AI判定9件の保持を確認。実企業300件の性能・検索精度を検証した結果ではない。既存美容院100件に新しい営業準備を自動実行していないため、追加検索／AI課金も発生させていない。実送信はOFFのまま。

## 目的

列名が異なる顧客保有CSVを、取込前に内容を確認して安全に企業リストへ追加できるようにする。

## 実装

- UTF-8 CSVのヘッダー、総行数、先頭5行を取込前に表示する。
- 会社名、WebサイトURL、電話、メール、住所へCSV列を対応付ける。
- 標準英語列と一般的な日本語列は自動選択する。
- 最大5MB、1,000行の既存制限をプレビューと本取込で共通適用する。
- 会社名欠落と不正URLを行番号・理由付きで収集ジョブへ保存する。
- エラーがあるCSVジョブからUTF-8 BOM付きの行別エラーCSVを出力する。
- エラーCSVにもプロジェクト所有者のアクセス制御を適用する。

## API

| Method | Path | 内容 |
| --- | --- | --- |
| POST | `/api/projects/{id}/collection-jobs/csv/preview` | ヘッダー・先頭5行・推奨列対応を返す |
| POST | `/api/projects/{id}/collection-jobs/csv` | `column_mapping`を使って取り込む |
| GET | `/api/collection-jobs/{id}/errors.csv` | 行別エラーをCSV出力する |

従来の標準列CSVは`column_mapping`を省略しても取り込める。

## 店舗単位の取り込み

「企業収集」→「CSVインポート」→「取り込み単位：店舗単位」を選択する。
同一チェーンの別店舗や、同じ予約サイトに掲載された別店舗を保持できる。
初期値は従来の企業単位。URL直接入力・検索収集の重複判定は従来通り。

- 店舗単位は店名と住所で識別する。住所がなければ店名とURLを使用する。
- 同じCSVの再取り込みは重複として除外する。DBの店舗キー一意制約で同時登録も防ぐ。
- 店名と住所は初期状態でWeb再解析から保護する。
- `website_url` は公式サイト、任意の `reference_url` は予約・出典ページ。
- 既知のポータルURL（HOT PEPPERなど）がWebサイト列にある場合、店舗単位では参考URLへ移し、公式サイトURLを空欄にする。
- 参考URLをWeb解析・フォーム事前解析・フォーム送信先として使用しない。公式サイトからポータルへの転送も参考URLへ分離する。
- Suppressionは公式サイトと参考URLの両方について確認する。
- 同じプロジェクトで別店舗とメール宛先・フォームURLを共有する場合、連絡可否を `PROHIBITED / shared_location_destination` として停止する。担当者のメールとForm ProfileのURLも確認し、店舗固有の連絡先が確認できるまで送信しない。
- 企業一覧の詳細画面で参考ページを開ける。CSV出力にも登録単位・参考URLを含める。

APIは既存CSV endpointのFormパラメーター `record_type=location` を使用する。
`company` が既定値。不明な値は422。任意の列対応 `reference_url` を追加した。
標準CSV列は `company_name,website_url,phone,email,address`、参考URLがあれば
`reference_url` を追加する。ExcelはUTF-8 CSVへ変換して取り込む。

住所が市町村名だけの場合、同名の別店舗を区別できない場合があるため詳細住所を推奨する。
取り込み時の店舗キーは維持する。手動編集による店名・住所の変更では別店舗を自動作成しない。
企業／店舗モードを跨いだ登録は別の単位として保持されるため、同じリストのモードを途中で切り替えない。
重複候補の検討・手動統合、送信先の重複送信防止、連絡禁止、承認境界は既存機能を維持する。

## DB更新と復旧

Migration `c7a24d9e601b` は既存Migrationを書き換えず、登録単位・店舗キー・参考URLを追加する。
既存企業はすべて `company` のまま。ドメイン・Webサイト・店名住所の企業一意性を
企業単位のpartial unique indexで維持し、店舗単位には店舗キーのunique indexを使用する。

店舗データが存在する場合、旧版へのdowngradeはデータを失わせず明示的に停止する。
旧版へ戻す際は更新前バックアップを別DBへ復元する既存復旧手順を使用し、店舗データを退避・移行する。
業務DBでMigrationや取り込みを試さず、更新前バックアップと独立環境で確認する。
