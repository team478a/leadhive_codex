# Phase C5: 作業キューへの復帰と再診断

## 目的と操作

停止理由別の作業キューで企業詳細を開いた後、同じ固定リスト・絞り込みへ戻り、最新の診断から次の対象を確認する。送信・承認・補完ジョブを追加する工程ではない。

1. C4の作業キューで状態／理由を選び、必要なページから「詳細を開く」。
2. 既存企業詳細で確認・修正を行い、変更する場合は既存の保存ボタンで保存。
3. 「作業キューへ戻る」を押す。
4. Projectと固定リストは復元される。「窓口診断を集計」で新しい診断を取得。
5. 元の状態・理由・ページ位置で更新結果を確認して次の企業を開く。

戻る操作で未保存の編集内容を自動保存しない。注意文を戻るボタンと同じ場所に表示する。保存・取消の既存UIを引き続き使用する。

## 保持する情報

Workspaceのメモリ内にProject ID、固定リストID/hash、状態フィルタ、理由コード、ページ位置だけを保持。会社データ、診断行、文面、送信者、承認情報を保存しない。localStorage、URL、外部サービス、DBへ戻り先を保存しない。ブラウザ再読込・ログアウトで復帰情報は失われる。

固定リストとhashが一致する場合だけ復帰フィルタを使用。新しいProject／固定リストには旧条件を適用しない。詳細遷移時に実際に表示したページ番号を保持し、再診断で候補数が減った場合は最終有効ページへ表示を丸める。理由コードが新しい診断範囲から消えた場合は「以前の理由・今回の診断範囲に該当なし」と表示し、別理由へ自動変更しない。利用者が「すべての理由」等へ変更できる。

## 再診断と安全境界

戻った時点では以前の診断結果を表示せず、再集計を案内する。既存のProject／cohort GETを再取得し、明示操作でC3診断の保存済み情報を読み直す。各ページは観察期間の診断で、承認・送信のsnapshotではない。

集計開始時に前の結果を消し、受信・検証済みページだけを部分集計へ追加。権限拒否・context競合・通信失敗でも以前の成功結果へ戻さない。C4の中断・generation検査と固定分母・context/hashの検査を維持する。UNKNOWN、共有窓口、Suppression等の禁止・要確認を解除しない。戻る操作はapprove、dispatch、retryを呼ばない。

権限と対象範囲は既存APIで再確認する。復帰情報は権限の代替ではない。通常の企業一覧・追客・返信導線と作業キューの復帰を分離。Dots、worker、実企業サイト、SMTP／Form POSTへの新しい接続なし。

## 変更と互換性

Frontendのみ。`CompletionReturnContext`を共通の型として使用し、App→Dashboard→Lead Completion→診断に戻り先を渡す。作業キューのフィルタを診断コンポーネントへ移し、再集計中に一覧が消えても保持する。選択UIと既存Company詳細は再利用。

Model、Migration、Backend API、認証、承認・送信・台帳の変更なし。既存の500kB超bundle警告は継続。

## 検証項目

専用_test DBの合成データでdesktop/mobileを確認する。

- 同じProject・固定リストへの復帰と、旧診断が表示されないこと。
- 状態・理由コード・2ページ目の復元、理由が消えた際の該当なし表示。
- 企業詳細で連絡禁止を実APIへ保存した後、再診断で本人が連絡禁止、同じ共有窓口の24件がSuppressionによりBLOCKEDへ変化すること。
- 件数減少時のページ丸め、禁止候補がHOLDの作業対象から外れること。
- 診断の403応答では旧結果に戻らず、診断0件・完了扱いなしとなること。
- 外部URL、approve、send、dispatch、execute、test-sendへのアクセスなし。

UNKNOWN／消えた理由の表示条件はテスト内の応答fixtureで確認する。実送信の記録を作らず、禁止変更も合成企業に限定する。実100店舗の変更・再解析や稼働環境反映は行わない。

ローカル結果: Frontend typecheck/lint/build成功。desktop/mobile E2E 2件成功。専用DBのMigration headへのupgrade・model差分なしとAPI起動を確認。最初の画面テストは共有窓口へのSuppression波及を1件停止と誤って想定して失敗し、既存安全制御を維持したまま「本人1件＋共有窓口24件停止」へ期待値を修正して再実行した。Backendのコード変更はなく、全体回帰はGitHub CIで確認する。

## 次工程候補

根拠付き下書きの再準備が必要な対象を、構造化した停止理由で絞り込めるようにする。現在の窓口理由とDM未準備理由を区別し、送信・承認境界を維持する。
