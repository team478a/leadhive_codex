## 0. 結論

収集から送信対象までの無駄を減らす方向性は妥当。ただし、元の案の基準 `main@49d4276` は古く、現行コードと異なる記述がある。特にフォーム起点収集（214）はすでにフォーム解析を予約する経路を持つ。また、`form_first` は `collection_jobs.source` の値ではないため、収集ジョブのsource別件数だけでは測れない。

実装は次の順に分ける。

1. **PR-0 利用状況の可視化**：本番DBに対する読み取り専用の集計と、件数の解釈に必要な制約を提供する。PR-0が完了するまで削除・停止を伴うPR-3には進まない。
2. **PR-1 収集後の解析**：会社起点など、現時点で自動予約されない入口を確認してから自動化する。214の既存予約を重複させない。
3. **PR-2 コスト削減**：AI対象を絞り、SNS追加検索の新規既定値を0にする。既存の保存済み設定は変更しない。
4. **PR-3 機能整理**：PR-0の実測と田中さんの確認後に、入口を停止・非表示・削除する。既存データや履歴は削除しない。

この文書はコード調査の結果であり、本番データの実測値ではない。本番DBを照会しておらず、利用件数・稼働中ジョブ数・実際の支出額は未確認である。

## 3. PR-0：利用状況レポートの設計

### 3.1 表示方法

まずは管理画面に運営者限定の読み取り専用レポートを追加する。管理者APIは `current_admin` で保護し、非管理者は既存方針どおり404にする。CLIだけにするとRender等の本番実行環境・DB接続権限・出力の受け渡しが別途必要になるため、UI/APIの方が確認経路として直接的である。

レポートは機能ごとのCOUNTと集計値だけを返す。会社名、URL、問い合わせ内容、検索語、条件提案本文、prompt、メールアドレス、企業IDの一覧は返さない。SQLはDB側のCOUNT/GROUP BYで実行し、行単位のPythonループは使わない。期間はUTCの直近90日とし、併せて全期間の有効中job/batch数を別枠で出す。

### 3.2 必須の指標とラベル

| 指標 | 集計元 | レポート上の意味 |
|---|---|---|
| CollectionJob | 90日分を `source`、status別にCOUNT | 収集job数。企業の検索API呼び出し回数とは区別 |
| 収集企業 | 90日分のCompanyを `source` 別にCOUNT。`form_first` を独立表示 | 保存企業レコード数。job数・検索回数とは区別 |
| OperationJob | `operation_type`、status別COUNT。別に現在の `queued` / `running` をCOUNT | operationの作成数と稼働中数 |
| Form delivery | `form_delivery_batches` のstatus別件数、最終作成時刻、関連する未完了job | 過去利用と未処理の安全確認。OFF設定だけで未使用と断定しない |
| 外部検索API | `LeadProcessingUsage.kind='search'` をprovider/status別にCOUNTし、費用推定の合計とNULL件数も表示 | 計測済みリクエスト記録・推定値。未計測経路を含まない可能性を併記 |
| AI | `LeadProcessingUsage.kind='ai'` をprovider/model/status別にCOUNTし、費用推定・tokenのNULL件数も表示 | SDK操作の観測。物理リクエスト数、全AI利用量、請求確定額とは断定しない |
| SNS検索 | `ExternalPresenceSearch` をplatform/status別にCOUNT | 外部検索の試行記録。開始後中断などがあるため「完了API回数」と表示しない |
| 条件 | `CollectionConditionRequest` と `CollectionFactReview` を別々にCOUNT | 確定条件revision数、人による事実確認数。提案呼び出し数ではない |
| 条件提案 | 新設するイベント記録を90日分COUNT | 記録導入後だけ計測可能。過去期間の欠損を「0」と表示せず「計測開始前」と表示 |
| RAW/レビュー | RAW benchmark、query run、review session、lead review、pair reviewごとのCOUNT | 実験・人手確認の種類別件数 |
| PC/live入力 | 既存 `activities` の記録を分かる範囲で分類 | 既存分は推定値。今後は内容を保存しない専用イベントで計測 |
| CF7 fixture | `cf7_observations` の有効/期限切れ件数 | controlled fixtureの観測のみ。本番フォーム利用数ではない |

`LeadProcessingUsage` は観測範囲が部分的で、プロセス中断時に未commit分が失われる可能性がある。計測率を証明できないので、レポートには「計測済み」「全体を網羅する保証なし」を常時表示する。NULL費用を0に換算せず、費用推定の合計とNULL件数を並べる。

提案APIは現状statelessなので、過去90日分を埋めることはできない。将来イベントは呼び出し時刻・成否・必要ならparser version等の最小メタデータだけにし、提案本文や利用者入力は保存しない。実際に外部AIを呼ぶよう変更する場合は、処理種別と課金情報を別の計測要件としてレビューする。

### 3.3 3,000社規模の安全性

- レポートを合成データで検証し、COUNTクエリ数に上限を設ける。
- 90日境界・UTC、status別、NULL費用、未計測の条件提案をテストする。
- 非管理者・未ログイン利用者の拒否をテストする。
- 集計行数は機能カテゴリ数に比例させ、企業ごとの明細を返さない。
- 実データ件数はPR作成時に推定せず、本番反映後に田中さんがレポートで確認する。

## 4. PR-1：収集から解析までをつなぐ

目標は収集された会社を必要な解析へ自動で渡すこと。まず各入口（会社起点、フォーム起点、CSV、URL、記事抽出）について保存関数とjob予約の有無をテストで固定し、未予約の入口だけを変更する。

- 1社のサイト解析内でトップページと問い合わせページの取得結果を再利用する。取得したHTMLの保持は1社のjob内だけとし、DBへ保存しない。
- 214フォーム起点の同一job内で既に取得した問い合わせページがある場合は、それを解析へ渡し、再取得しない。jobをまたぐ場合は再取得を許容する。
- 既存のweb/form解析操作は `site_analysis` を呼ぶ形へ移し、既存OperationJob履歴は残す。重複予約を防ぎ、予約は200件単位でcommit・`expunge_all`する。
- 解析完了後に既存 `form_dm_readiness` を予約する。同プロジェクトでqueued/runningなら重ねて作らない。
- 自動予約は設定でOFFにできる。未解析一括実行も上限・進捗・再開を持つ。
- URL・タイトルだけで確実に除外できる非企業候補に限定し、保存前除外を追加する。曖昧な候補の既存sendability判定は残す。
- 同期解析APIは直接処理をやめ、jobを作って202を返す。画面は進捗を表示する。
- 取得上限・旧処理との出力比較・同一URLのfetch回数を合成fixtureで検証する。実サイトにはアクセスしない。

## 5. PR-2：AI・SNS追加検索の無駄を減らす

- AI判定の既定対象は、送信可否が `READY` / `BROWSER_READY`、またはフォーム確認待ちの会社に限定する。メール案件はメールアドレスあり・連絡禁止でない会社を対象にする。
- 「全件」は明示的な詳細設定のみに残し、対象数とAPI利用見込みを実行前に表示する。
- 新規 `PresenceSearchPlan` の `max_extra_searches` 既定値を0にする。保存済みplanは更新しない。必須媒体の動作を変えない。
- 合成データで対象数・明示的全件選択・既存設定維持をテストする。外部APIは呼ばない。

## 6. PR-3：実行経路・収集元・不要機能の整理

**PR-0の本番結果を田中さんが確認し、未完了のjob/batchの扱いを決めてから着手する。**

### 6.1 検索経路

- 新規の検索収集をスケジューラ/計画実行へ寄せる。フォーム起点も同じ予算・再開・進捗の制御へつなぐ。
- 同期 `POST /collection-jobs/search` は画面参照がないこと、外部利用者・自動化からの依存がないことを確認してから停止する。
- 古いworker経路は新規作成を止めても、既存queued/running jobを最後まで処理できるよう残す。実行中・待機中がゼロになったことを実測してから削除する。
- 過去のCollectionJob・OperationJob履歴と結果表示は保持する。

### 6.2 収集元

- Google検索、CSV、URL、記事抽出は維持する。
- Google Maps Platform Termsの現行§3.2.3(a)は、Google Maps Contentをサービス外に保存する例としてbusiness names/addressesのコピー保存を挙げている。[公式規約](https://cloud.google.com/maps-platform/terms)。新規のGoogle Maps由来収集は、契約・法務確認が完了するまで止める方針とする。これは法的助言ではない。
- 停止は画面の選択肢だけでなく、API、scheduler、worker、再開処理すべての新規経路に適用する。既存データはこの整理PRで削除しない。保持・削除は田中さんが専門家に確認して別途決める。
- gBizINFOは収集sourceの選択肢から外す場合も、法人確認の用途まで削除しない。

### 6.3 旧フォームDM・検証機能

- 旧一括フォームDMの画面・新規作成API・worker入口を整理する。`form_delivery_batches` 等の履歴、送信結果、二重送信防止に必要な記録・テーブルは削除しない。
- 実測でactive batch/jobが残っていれば、停止前にcloseout手順を決める。設定OFFだけで削除安全とは判断しない。
- RAW/レビュー、CompletionBenchmark、PC/live試行、CF7候補、controlled lab等を運営者限定にする場合、画面とAPIを両方保護する。既存 `current_admin` を利用し、外部企業利用者へ管理者権限を付けない。
- 検証機能を削除するか、管理者限定で残すかはPR-0実績と田中さんの決定に合わせる。実利用があれば即時削除しない。

### 6.4 収集成果UI

収集元・方法、検索語、実行数、保存・除外・重複、検索100回あたりの送信可能企業数を「収集の成果」にまとめる。AI判定レビュー精度は折りたたみ等へ分け、母数・計測範囲が分からない指標を成功率のように見せない。
