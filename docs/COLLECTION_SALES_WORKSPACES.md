# 収集と営業の画面分離

基準main：`2639c7020606771edff224ecde274f67e95176dd`（PR #90）。

## 利用フロー

ログイン後は「収集ターゲット設定」を表示する。

| 担当作業 | 操作 |
|---|---|
| リスト収集 | ターゲット設定 → 収集開始 → 収集リストの確認 |
| 営業作業 | 営業準備 → 企業一覧・DM準備 → Human承認 → 配信結果 |

収集担当はリスト名・対象プロファイル・地域を保存し、「保存して収集へ」で
収集画面に進む。選んだ対象のキーワード・地域を引き継ぐ。
件数を確認して「収集を開始」を押すまで検索を実行しない。
既存のサービスURL分析・ターゲット提案も再利用する。今回はAI APIを実行しない。

保存済みターゲットを選んで再利用できる。上部に収集の3段階を表示し、
サイドメニューを「リスト収集」「営業作業」「管理・ガイド」に分ける。
営業準備パネルを収集画面から移し、収集条件を画面の先頭に置く。
収集側の処理履歴から営業準備ジョブの操作を外す。

収集リストの確認は通常ProjectのCompanyデータを使う。
20件ずつ表示し、企業サイトリンク・問い合わせ候補・対象外/連絡禁止を表示する。
既存CompanyCollectionFeedbackを再利用し、対象企業のOK/NGから確認できる。
問い合わせURLの確認・修正へ切り替え可能。DM作成と承認は営業画面で行う。
承認済みのクリーニング済み候補には、[一括送信開始](CLEAN_LIST_BULK_SEND.md)の導線を設置する。
以前のRaw Benchmark画面は管理側に「検証用」として残し、通常リストと混同しない。

営業担当は同じProjectを選んで既存営業準備を実行する。
企業一覧・承認キュー・配信結果へProjectを引き継ぐ。
プロジェクト管理、プロファイル編集、CSV/URL、条件確定、検索上限、追加調査、
既存Web解析・AI判定・定期収集の機能は維持する。
日常作業の入口ではアーカイブ済みProjectを除き、管理画面から従来どおり参照できる。

## 安全と権限

画面を分ける変更であり、新しい職種別権限は追加しない。
既存owner/editor/viewerを維持。閲覧者には収集実行・営業準備・レビュー記録を出さない。
バックエンドのProject境界・Human承認・営業NG・Suppression・UNKNOWN再送禁止を変更しない。
表示・保存・画面遷移だけで収集/解析/DM生成/承認/送信を自動開始しない。
ターゲット保存は既存Project保存API、レビューは既存Feedback APIを使う。
既存データの移動・一括補正・削除、DB/API契約/Migrationの変更はない。
ProjectFormは保存したProjectを親画面へ返すが、通常管理画面の保存操作は維持する。

## 試験

専用 `_test` DBとlocalhostで実施する。新しい導線のAPI mock試験では、
対象保存、明示収集POST、結果確認、営業移動、Project引継ぎ、viewer、非送信を検証する。
都市候補もmockし、実検索API・実企業サイト・送信は使用しない。
既存のProject CRUD、Collection Conditions、CSV、Form Intelligence、営業準備、
Desktop/Mobile navigationの回帰試験も行う。
最終headの検証件数とCIリンクはPRに記録する。

## 制限

収集の品質やフォーム成功率を改善したという変更ではない。
営業準備の既存処理は検索・解析・AI・DM下書きを含むが、Humanが専用画面で明示開始する。
収集リスト確認は既存allPagesを使い全保存候補を取得し、表示を20件に区切る。
大量データの通信量最適化・職種別ACL・永続的な画面選択は今回の対象外。
本番反映はマージ後の別工程。既存の設定・配布パッケージ・本番データは変更していない。
