# 212 「送信の準備・実行」画面の流れの作り直し

2026-10-17の実装仕様。送信フローを文面作成から結果確認まで順番に進められる構成にする。実装はバックエンド（PR-A）と画面（PR-B）に分け、自動マージ・デプロイしない。

## PR-A: バックエンド

- `POST /api/projects/{project_id}/outreach-drafts/bulk-from-template` を追加する。テンプレート、メール／フォーム、最大500社のIDまたは `NO_FORM_DRAFT` を受け取り、OperationJobで処理する。
- AIを呼ばず、100社ごとにcommitし、セッションをexpungeする。連絡禁止・suppression・現行の送信可否判定を確認し、対象外理由を記録する。
- 会社に既存Draftがあれば連絡方法を問わずスキップする。本文の会社名などの差し込みを行い、承認・予約・送信は作成しない。フォームDraft作成後はフォーム送信可否の再集計をキューする。
- メール／フォームテンプレートは停止・連絡辞退の方法を本文に含める。フォーム本文1,000文字超は警告扱いとし、APIでは拒否しない。
- `GET /api/projects/{project_id}/send-flow-summary` はSQL集計のみで、対象、Draft、フォーム確認、承認、当日送信・予約、結果件数を返す。

## PR-B: 画面

- ①テンプレート、②送信先・文面、③フォーム確認、④承認、⑤送信、⑥結果の順に配置する。
- 既存パネルを作り直さず、折りたたみ式の段階として並べ替える。次の段階へ進む操作を設け、メールのみならフォーム確認を飛ばす。
- テンプレートに会社名・送信者情報の差し込みと会社プレビューを設ける。承認・送信・結果は既存パネルを再利用する。

## 変更禁止

- 承認なしの送信、自動承認、送信上限、送信時間帯、連絡禁止、二重送信防止、結果不明の再送禁止を変更しない。
- 既存Draftを一括テンプレートで上書きしない。メール配信停止リンクは既存の配信処理が自動で付与する。
- 企業一覧・承認キュー・メール配信状況の各ページは残す。
