# 検索テンプレート成果分析 実装記録

## 目的

定期検索テンプレートごとの収集成果を比較し、保存につながる検索条件と重複が多い検索条件を判断できる
ようにする。

## 記録方法

バックグラウンド検索がキーワード単位の `collection_jobs` を作成するとき、実行元の
`operation_job_id` と `search_schedule_id` を記録する。テンプレートや処理履歴を削除しても収集履歴を
失わないよう、関連先削除時は外部キーをNULLにする。

手動検索や過去の収集ジョブは特定テンプレートの成果へ混ぜない。

## 集計指標

| 指標 | 計算 |
| --- | --- |
| 検索数 | 作成されたキーワード別収集ジョブ数 |
| 発見 | 外部検索から得た候補数 |
| 保存 | 重複・不正データを除いて保存した企業数 |
| 保存率 | 保存 ÷ 発見 × 100 |
| 重複率 | 重複 ÷ 発見 × 100 |
| エラー | 入力・外部サービスエラー数 |

発見数が0の場合の率は0%とする。率は小数第1位へ丸める。

## API・画面

`GET /api/projects/{project_id}/search-analytics` は所有プロジェクトのテンプレートを保存数の多い順で返す。
まだ実行していないテンプレートも0件として含める。企業収集画面の「テンプレート別成果」表で各指標を
比較できる。

## 検証

同じ2社を2キーワードで取得するケースを実行し、発見4、保存2、重複2、保存率50%、重複率50%を
実PostgreSQLで確認した。Migration往復、バックエンド全テスト、Ruff、typecheck、lint、build、
デスクトップ・モバイルE2Eも実施する。
