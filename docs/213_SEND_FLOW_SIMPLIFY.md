# 213 送信画面の簡素化

作成: 2026-10-17。実装対象: `main@ee1d3ba`。バックエンドの承認・予約・送信判定は変更しない。

## 画面構成

- プロジェクトと連絡方法（フォーム／メール）を最初に選ぶ。連絡方法はプロジェクトごとにブラウザーへ保存する。
- メールは「文面をつくる／承認して送る／結果」の3段階、フォームは「文面をつくる／フォームを確認／承認して送る／結果」の4段階。
- 重複していた進捗カードをなくし、各段階の見出しに件数と状態を表示する。
- テンプレート編集・下書き作成・フォーム送信可否の詳細は「文面をつくる」にまとめる。メール下書き一括作成では、適格企業の選定を既存のサーバー側 `NO_EMAIL_DRAFT` 条件に委ねる。
- フォーム確認後は既存の確認結果を使い、承認キューと予約操作を「承認して送信予約」にまとめる。承認に成功して予約に失敗した場合は、同一の冪等キーで予約だけを再試行する。
- 結果段階では選択中の連絡方法の直近20件と件数を表示する。フォーム確認キュー、CF7候補、個別準備、Human Approval Queue は専用の承認キューに残す。
- 環境全体のフォーム送信上限は運用設定に置く。承認キュー内の既存フォーム運用パネルからは設定編集を外す。

## 既存APIの制約

- メールの24時間・1時間上限は現状、予約APIに渡す予約ごとの値であり、環境全体の値を取得・設定するAPIがない。既存の予約ごとの入力と既存値を維持し、環境共通の設定移動は未実装としている。共通設定APIを追加する場合は別途指示が必要。
- 送信フロー集計APIの結果件数は経路横断のため、段階見出しでは表示せず、結果パネルは選択中の経路ごとの既存配信APIを使う。
- 結果APIが持たないフォーム実行の開始日時は「開始日時未記録」と表示する。
- 送信フロー集計APIに既存フォーム下書きの作成日時がないため、集計の古さはこの画面で作成した下書きについてのみ検知できる。既存下書きが後から追加された場合は、手動で再集計する必要がある。
- API版・Worker版と版不一致の警告は既存の共通フッター表示を維持する。現在の送信フローAPIは選択チャネル別の本日送信・予約件数を返さないため、段階見出しでは経路横断件数を表示しない。

## 検証

`frontend/operator-guide.config.ts` のPC・スマートフォン構成に、経路分離、プロジェクト別記憶、テンプレートとサーバー選定下書き、承認・予約および同一キー再試行、承認キューの検証機能維持、運用設定へのフォーム上限配置を追加する。
