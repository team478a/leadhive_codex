# SMTP接続確認（送信なし）

## ゴール

配信サービス接続の前提として、保存済みSMTP設定の接続・暗号化・認証を、実メールを送らず管理画面から確認できるようにする。サービス固有の到達・苦情通知adapterは、サービス名が未確定のためこの工程では実装しない。

## 操作

1. 管理者で「運用設定」を開く。
2. SMTPホスト、STARTTLS用ポート、ユーザー名、パスワード等を保存する。
3. 「メールを送らず接続確認」を押す。
4. 結果、暗号化、認証、確認日時を確認する。変更した設定は再保存して再確認する。

認証なしのサーバーは「認証は未実施」と表示する。成功はSMTP接続の証拠であり、送信元の利用許可・相手への到達・開封・通知接続を保証しない。別の「テストメールを送信」は実メール送信であり、この工程では実行しない。

## 境界

- `POST /api/admin/smtp-settings/connection-test`。既存Human管理者認証を使用。一般ユーザーは404、未認証は401。既存Agent/Human分離を維持する。
- 保存済みDB設定を優先、なければ既存環境設定を使用。リクエスト本文の宛先・confirmed等は送信に利用しない。
- `OUTBOUND_ENABLED=false`でも利用可能。送信経路へは接続せず、SMTP接続、EHLO、STARTTLS、AUTH、QUITのみ。MAIL/RCPT/DATA/send_message/sendmailを呼ばない。
- STARTTLSは標準の証明書検証・ホスト名検証を必須にする。ユーザー名ありでSTARTTLSなし、パスワードなしは接続前に拒否する。
- 現行送信経路はSTARTTLSで、465のimplicit TLSは未対応。診断だけ成功させないよう465は設定段階で拒否する。提供元のSTARTTLS用ポートを設定する。
- 通信ごとのタイムアウトは保存値と15秒の小さい方。操作全体の15秒完了を保証するものではない。
- 外部例外やSMTP応答の生データ、資格情報はレスポンス・ログへ出さない。ログは管理者ID、成功可否、段階のみ。
- 結果は画面内のみ。設定を保存すると前の結果を破棄する。DB変更・Migration追加なし。

## 検証

- Backend: 新規診断・既存SMTP設定・送信停止guardの44テスト成功。全Backend suite再実行とは区別する。
- Ruff、compileall、Frontend typecheck/lint/build成功。APIはE2E用プロセスで起動成功。
- 専用テストDBのAlembic upgrade/checkはBackend fixtureで実行。Migration変更なし。
- SMTPはmockのみ。送信関数が一度も呼ばれないこと、TLS検証、認証失敗、秘密情報の非露出、権限、送信OFF時の動作を検証。
- PC・スマートフォンのE2E 2件成功。未設定エラーを実APIで確認し、成功表示はHTTP mockで確認。実SMTPへの疎通とは区別する。
- このPCのAPIソース・Web静的ファイルを更新し、APIを再起動。health、診断APIの公開、送信・Agent・承認メール・通知受信flagのOFFを確認。企業100件、メール/フォーム送信0件を保持。実SMTP設定は未保存。

## 残る工程

配信サービス選定、サービス固有の署名・アカウント・宛先・Message-ID照合、通知adapter、公開HTTPS受信または提供元APIによる取得方法の選定。ローカルPCへ外部通知が到達する経路はまだ構築しない。実送信・Agent・通知受信はOFFのまま。
