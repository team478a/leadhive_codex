# 運用中に見つけた営業NGの登録

基準: main `31f7bcde987057d3c0f141bf25cc8e6528d8314d`。

## 使い方

企業一覧で対象企業の「詳細」を開き、営業NGの理由を入力して
「営業NGリストへ移す」を押す。禁止表示・連絡拒否を人が確認した場合に利用する。
理由が空の状態では登録できない。登録後は登録済み表示になり、再登録ボタンを隠す。

既存の `/api/companies/{id}/contact-control` を再利用する。
`do_not_contact=true`、理由の先頭を `営業NG：` とし、既存の禁止理由を付記する。
既存APIで営業状況は対象外になり、SuppressionとActivityにも記録される。
Companyを削除・別Projectへ移動する操作ではない。
フォーム候補の集計の「営業NGリスト」に分類される。

所有者・編集者のみ登録可能。閲覧者には登録操作を表示しない。
権限・Project境界・連絡禁止の強制は既存APIで維持する。
この操作では連絡先品質を変更せず、未保存の品質編集値も使用しない。
既存の営業NGは再解析で自動解除しない。解除用の新操作は追加しない。
従来の管理者向け連絡制御編集は維持する。

## 検証

Desktop/Mobileで、理由必須、登録済み表示、既存理由の保存、品質維持、
APIに保存された対象外状態、NGリスト分類、Core permissionのPROHIBITED、
再読込後の保持、Viewerの登録操作非表示を検証する。
テストデータは専用の `_test` DBと合成企業のみ。

実行結果: 新規手動NG登録と既存フォーム画面のE2EはDesktop/Mobile計4件成功。
Frontend typecheck・lint・build成功。
既存の企業管理・連絡許可・フォーム候補集計のBackend回帰テスト32件成功。

DB変更・新API・外部取得・実企業への入力・承認・メール/フォーム送信はない。
本PRは手動NGの登録操作であり、汎用ブラウザ入力ランナーの本番接続ではない。
ブラウザ入力は引き続き模擬環境まで。実運用への接続は次工程として残る。
